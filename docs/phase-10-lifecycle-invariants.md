# Phase 10 production lifecycle invariants

| Boundary | Authoritative owner | Allowed transitions | Required release / rollback | Immutable state | Retry and crash semantics | Lock / transaction boundary |
|---|---|---|---|---|---|---|
| Native materialization | Phase 10 projection/proposal reducers | evidence → eligible proposal; `DISABLED` → `PENDING` only on newer eligible evidence | Timeout returns no proposals; legacy scheduling continues | terminal `TRIED`/`EXPIRED`; evidence revisions reject stale writes | Reads are best effort and bounded to 2.5 seconds per country | No scheduler-owned DB transaction; canonical term → projection → proposal |
| Phase 8 selection | Frontier allocator | `PENDING` proposal → `RESERVED` decision | stale candidates fail closed; reservations older than 20 minutes become `RELEASED` | selected neighborhood and proposal evidence snapshot | allocation IDs are deterministic; orphan reservations are reclaimed under allocator authority | allocation advisory lock → canonical term → projection → proposal row → decision |
| Query construction | Query Intelligence | immutable allocation → governed query or no query | invalid construction atomically creates `DEFERRED` decision and terminal `EXPIRED` proposal | native term, evidence checksum, proposal/decision IDs, target key and all target dimensions | retry cannot reselect or evidence-refresh a quarantined identity | no provider access; no independent planner or quota ownership |
| Diversity / authority checks | Autonomous scheduler | reserved query → schedule candidate | every skipped/rejected candidate performs `RESERVED` → `RELEASED` | Phase 8 snapshot and query lineage | released decisions consume no Phase 8 quota; a later opportunity may allocate useful work | release is a guarded atomic update |
| Scheduling and Phase 9 | Scheduling transaction and Phase 9 retrieval policy | decision `RESERVED` → `COMMITTED`; proposal `PENDING` → `TRIED`; run/job/reservations created | any mismatch or failure rolls back run, job, Phase 9 reservation, decision commit, and proposal consumption | Phase 8 neighborhood dimensions; query lineage; terminal proposal state | one transaction makes reserve/schedule/consume crash-atomic; queue idempotency key is run-scoped | query reservation → Phase 9 reservation → decision commit → proposal consume → job, all in one transaction |
| Execution / continuation | Phase 9 workers | `SCHEDULED` → `RUNNING` / retry → `COMPLETED` | existing worker and quota recovery release failed work | allocation origin, run metadata, retrieval configuration | job locks and idempotency keys recover process failure without a second allocation | Phase 9 owns provider, quota and continuation state; Phase 10 never calls providers |
| Completion | Query-run completion transaction | non-completed → `COMPLETED` exactly once | transaction rollback keeps run and attribution unchanged | first terminal metrics and `completed_at` | terminal replay is a no-op, including components, quota and analytics | query row update, outcome, attribution and quota consumption share one transaction |
| Attribution | Completion transaction | absent attribution key → one attribution row | rolls back with completion | allocation evidence snapshot, first terminal metrics | first-write-wins exactly matches query completion; retry cannot drift | reads only the committed decision snapshot, never the mutable proposal |

## Lifecycle model

Phase 10 proposes evidence but never owns retrieval. Phase 8 is the sole allocator and snapshots both evidence and the exact executable neighborhood. Query Intelligence is the sole query-construction authority. The scheduler must resolve every reservation exactly once: release, defer-and-quarantine, or atomically commit it with a run while consuming the proposal. Phase 9 remains the sole provider/quota/continuation authority and may not change the Phase 8 neighborhood. Completion and attribution are one first-terminal-write transaction.

The evidence/allocation lock order remains creator row → canonical term → projection → proposal → allocation decision. The separate scheduling transaction locks the query reservation, then Phase 9 reservation, then the already-created allocation decision and proposal; projection reducers and proposal materializers never lock query/Phase 9 rows, so this does not form a reverse edge. Materialization never waits indefinitely while the scheduler lock is held, and no lifecycle path acquires an earlier evidence lock after a later one.
